# Modular Profile Hot-Swap — Discussion (design-commentary) — 2026-06-06

**Project:** svg-mb-control
**Status:** design-commentary, non-normative; companion to `docs/modular-profile-hotswap-plan-2026-06-06.md`

This document is opinion and analysis grounded in the code, the decision record (D1–D7 in `docs/profile-hot-swap-decision-2026-06-03.md`), and the deepening plan. It authorizes nothing. FEAT-0003 stays exactly where the maintainer recorded it: not scheduled, not a net benefit, design-capture only (`docs/features/FEAT-0003-selectable-profile-hot-swap.md:16-23`). Every "would/could" below describes unbuilt behavior; every opinion is labeled as such. The point is not to argue the feature should be built — it is to judge, honestly and against the source, whether the *seam* is worth designing and whether any single slice has standalone merit. Because that status holds across the whole document, the sections below reference it in a clause rather than re-citing it each time.

The through-line is a tension between two things that are both true: the per-channel control law sits behind a single, genuinely well-placed seam, and the maintainer doubts the feature that seam would enable. A well-placed seam is an asset even unbuilt — it records, once and with grounding, the answer to a question that keeps recurring ("can't we just swap in a PID?"). But a worked-out plan for a doubted feature is also a liability: it must be kept true as the code drifts, and a sufficiently detailed plan generates its own gravity toward being built. Each section below holds one element of the design against that tension, keeps only the grounding needed to support the judgment, and closes with the single fact that would flip it.

## The premise: should a swappable control law exist at all?

**What the element is and the decision it embodies.** This is the load-bearing framing in §0 and §2 of the deepening plan: before any dispatch table or PID class is discussed, the documents stake out *why a swappable control law is being written down at all when no one intends to build it*. The decision embodied is a deliberate non-decision — to capture a design seam in prose and hold it at arm's length from implementation. The plan quotes the maintainer verbatim (plan §0, sourcing `docs/features/FEAT-0003-selectable-profile-hot-swap.md:16-23`): the feature "is not believed to be a net benefit and is not planned," and "PID is recorded as the worked **example of the range**." FEAT-0003 sits at `Draft` in the registry of `docs/features/README.md`, whose process section defines `Draft` as "planning, not a backlog to start, and not permission to write code." So the doc's existence is not a rogue act; it occupies a sanctioned lifecycle state. The meta-question is whether occupying that state *here*, for a doubted feature, is worth the words.

**The real tension.** Two costs point opposite directions. A written seam has option value: if the swap is ever wanted, the hard thinking — where the seam goes, what carries over on a swap, how the measurement gate is honored — is already done and grounded. But YAGNI says the cheapest design for a feature you will not build is no design, and a detailed plan is not free: it must be kept true as the code underneath it drifts, and a sufficiently worked-out plan generates its own gravity toward being built. The doubt is the whole point of the tension. If the maintainer were merely *deferring* a wanted feature, capture would be obviously sound. Capturing a feature the owner actively believes is net-negative is the sharper case.

**The strongest case for the alternative (steelman).** Documentation must be maintained or it lies, and this doc is already drifting against the code it cites. The plan itself concedes this: its §8 is a "reference-drift correction" admitting the `channel_evaluator` citations slid roughly five lines after commit `33f8d24`. That is a doc that has *already* required maintenance for a feature no one is building — exactly YAGNI's prediction. The plan also has to carry careful scoping to stay true: its "no runtime law selection" claim holds only for the *control* worker — the only `--profile` flag in the repo is the unrelated offline analyzer's (`src/analyze/analyze_cli.cpp:294`) — a distinction a casual reader could miss. A steelman concludes: every line of a doubted-feature plan is a future liability that will silently rot, and the honest YAGNI move is to keep only the one-paragraph FEAT-0003 stub and delete the deepening.

**What it actually costs in this codebase.** The grounded facts make the seam's *absence* concrete, and that is what bounds the doc's real cost. Today the law is a single free-function call at `tick_runner.cpp:241-243` with no interface; `control_loop_config.cpp` contains no `controller` or `control_law` discriminator (a grep returns nothing), so the law's kind cannot be selected at startup or runtime; and config is welded to dynamic state in `ChannelState` (`src/control/control_runtime_context.h:17-18`), whose body carries `smoothed_demand_pct` (`:32`), `boosts[]` (`:35`), and the `low_band_*` accumulator block (`:53-69`) right next to `config` (`:18`). That weld is the load-bearing observation: any real swap is a state-ownership refactor first, not a drop-in (the plan reaches the same conclusion in its §2). The *cost of the doc*, concretely, is the maintenance surface it has already shown — at minimum the line-number citations into `channel_evaluator.{cpp,h}` that moved once and will move again on the next edit — multiplied across the ~390 lines of the deepening plus FEAT-0003's ~310 lines. That is a real recurring tax, but it is bounded and self-disclosed: there is a `tests/test_feature_specs.py` machine check (noted in `docs/features/README.md`) that catches registry/traceability drift, even if it does not catch line-number drift inside prose.

**Where I land and why (opinion).** The deepening plan's existence is justified, but narrowly, and not for the reason a feature spec usually exists. It is *not* justified as a build-readiness artifact — staging implementation for a feature the owner believes is net-negative would be exactly the "detailed plan creates pressure to build" failure mode, and the doc would be debt. It *is* justified as a **decision-durability artifact**: its genuine function is to record, once and with grounding, the answer to a question that will keep recurring so the maintainer does not re-litigate it from scratch each time. The §0 status guard and the repeated "would/could … proposal" labeling (e.g. plan §0) are what make this work rather than boosterism — the doc spends as much effort fencing off the build as describing it. On the specific sub-question — "is PID as the worked example of the range a sound way to design an abstraction you don't intend to build?" — my position is yes *for the stated purpose*: naming feedback-PID stress-tests whether the seam is wide enough (it forces the state-weld problem into view, plan §2), which a curve-only example would hide. That is sound as a *sizing* exercise. It would be unsound as a *construction* plan, and the doc is careful to be the former.

**What single fact would flip my view.** I would flip to "this is documentation debt, delete it" if the line-number drift already visible in §8 proves to be load-bearing rather than cosmetic — concretely, if a future reader (human or agent) acts on a drifted citation and makes a *wrong code decision* because the doc said `:435-469` and the function had moved. The §8 correction shows the precondition is already present. One demonstrated bad decision traceable to a stale citation would mean the maintenance cost has exceeded the decision-durability value, and the right move would be to collapse the deepening back into a citation-light FEAT-0003 stub that records *the decision* ("not a net benefit; not planned; seam would be a state-ownership refactor, not a drop-in") without the brittle file:line scaffolding that has to be re-verified on every touch of `channel_evaluator.cpp`.

## The skeptic's case: leave it on paper

The strongest reading of the maintainer's recorded judgment is not "wait and see" but "the paper artifact is already the whole return." The plan is honest that any build "would be a demonstration" (plan §6). What a demonstration demonstrates is that a seam *could* be cut — and the decision record (D1–D7) plus this plan already establish that, including the apply order, the state-ownership split, and the dispatch shapes, without touching a line of `src/`. The design has de-risked a future build: if a real requirement ever lands, the architecture is waiting. My opinion is that capturing that and stopping is the correct terminal state, because the marginal value of converting the design into running code is, on the shipped profile, zero, while every cost below is paid in live thermal-control code. The honest counter is that a design left unbuilt can rot or drift — and indeed §8 already documents the ~5 lines of file:line drift it had to correct. But drift in a design doc is cheap to re-ground (it just was); drift in a refactor of `channel_evaluator.cpp` is a regression in fan control. That asymmetry is the spine of the whole case.

Take the seam itself. D1 introduces `IChannelController` and D2 decides to move the curve law's dynamic state off `ChannelState` into a `CurveOverlayController` in one pass (`docs/profile-hot-swap-decision-2026-06-03.md:51-69`, `:86-107`). The tension is real: `EvaluateChannel` *is* a pure input→output function with a single call site at `tick_runner.cpp:241-243`, so the seam is genuinely well-placed, and the steelman for cutting it now is that doing it while the code is small is easier than doing it under a deadline later. But the D2 "full decouple in one pass" must reproduce today's output bit-for-bit — the boost-sum operand order at `channel_evaluator.cpp:353-364` carries a load-bearing comment citing `CONTROL_PIPELINE_MATH.md §5` precisely because left-to-right associativity is what keeps the result identical. The build's own gate (REQ-PROFILE-01) is "prove you changed nothing observable." A refactor whose acceptance criterion is *no behavior change* delivers, by construction, no shipped benefit. The single fact that would flip me on the seam: a second control law actually scheduled to ship live, at which point the one-call-site move stops being decoration and becomes load-bearing.

The dispatch and profile surface is where the "modular" framing is weakest by the plan's own logic. Proposal A would add a `controller` discriminator and a `MakeChannelController` factory; Proposal B would add a profile request file, a `TakeRuntimeProfileRequest` intake, an optional `--profile` selector, and per-channel status/CSV fields and `control_loop.profile_*` events (plan §3–§4). Today none of this exists: `LoadChannelConfig` (`control_loop_config.cpp:407-472`) is a flat monomorphic parse with no discriminator branch, the worker has no `--profile` flag (the only `--profile` in the tree is the analyzer's, `analyze_cli.cpp:294`), and profile selection is restart-only — the supervisor bakes one `--config <path>` into the worker command line (`control_supervisor.cpp:259-270`) and re-bakes it on every restart. The plan's §5 primitive table lists three net-new pieces marked missing — the `IChannelController` seam/factory, the `controller` discriminator + per-law parse, and the profile request file + intake — alongside three already-implemented primitives and one spec-only. The plan's *own* recommendation defers the registry (A2) until "a third law or external registration is wanted" (plan §3) and concedes it "earns its keep only once the number of laws exceeds the two-law demonstration" (plan §3). So by the document's own reasoning the modular layer pays nothing on the demonstration it is scoped to. And the restart path it would replace is not a latency problem: the control tick is 250 ms with a 250 ms write cooldown (`docs/MEASUREMENT_GATE.md:5-8`) over six live channels, so swapping tuning numbers via `--config` plus a supervised restart costs at most a few ticks. What would flip me: an operator workflow that must change the law *without* dropping fan authority across a restart, which the restart path genuinely cannot offer.

The deepest cost sits in the safety path, and it is concrete rather than rhetorical. The sensor-safe latch sets `evaluation.safety_override = true` inside the curve law at `channel_evaluator.cpp:263` when a channel hits three consecutive sensor failures and is forced to 100%; the write path reads exactly that field at `channel_write.cpp:307` (`if (channel.circuit_breaker_open && !evaluation.safety_override) return;`) to let a thermal-safety command bypass an open write-failure breaker. This is the recovery-gap remediation-3 invariant, pinned by a test that asserts "EvaluateChannel sets safety_override in sensor-safe mode" (`tests/cpp/channel_write_tests.cpp:284-285`, seam documented at `:8`). Plan §6 step 1 would pull that sensor-safe latch and `safety_override` *out* of `channel_evaluator.cpp` into a shared output stage. To be precise and not overclaim: that refactor would not by itself break safety. What it would do is relocate the field a thermal-safety breaker-bypass depends on, so the `:263`→`:307` invariant and the test that pins it would have to be re-proven against moved code — for a feature the maintainer rates as not a net benefit. Spending re-verification risk on the forced-100%-on-sensor-loss path to ship nothing observable is the trade I will not take. What would flip me: if the shared-stage extraction were independently motivated (a real second consumer of that conditioning), the safety re-proof would ride along on work that pays for itself anyway.

The second law and its measurement-gate path is where the skeptic's "uncharacterized" worry had teeth in the original D6 text. The characterized baseline is the curve+overlay law on the shipped 250 ms profile and channels 0–5 (`docs/MEASUREMENT_GATE.md:5-8`); any feedback law is, by definition, off that baseline. The original 2026-06-03 D6 posture routed PID through a non-writing shadow path by default but allowed `pid.allow_live: true` before characterization evidence existed; the 2026-06-06 revision now requires both characterization evidence and a non-NaN slew cap before live PID writes (`docs/profile-hot-swap-decision-2026-06-03.md` §D6). That revision closes the footgun this section originally identified. The steelman for building PID remains genuine: feed-forward `curve(temp)+overlays` cannot hold a *target* temperature under a disturbance the curve over- or under-shoots; only a feedback law closes that error. But the corrected gate reinforces the same conclusion: for a demonstration nobody is committed to shipping, a live feedback law should stay on paper until the measurement gate is actually planned to be cleared.

Where I land (opinion): leave it on paper — not "never" in the absolute, but *until one specific fact changes*, and the per-element flip conditions throughout this document converge on the same fact. The one scenario where building it would actually pay off is a **measured** control requirement the feed-forward curve provably cannot meet: a channel that must regulate a sensor to a target temperature under a disturbance where `curve(temp)+overlays` (`channel_evaluator.cpp:440-474`) demonstrably over- or under-shoots, *and* the `docs/MEASUREMENT_GATE.md` characterization evidence to run a feedback law live already exists. That is the only scenario where the alternative — restart with new curve numbers — cannot produce the required behavior at all, and where the gate that protects the shipped baseline is already satisfied rather than bypassed by a flag.

## The seam: IChannelController replacing EvaluateChannel

This element is the single structural change D1 names: replace the one direct call to the free function `EvaluateChannel` at `tick_runner.cpp:241-243` with a virtual `IChannelController::Evaluate`, and make the current law the first implementation (`docs/profile-hot-swap-decision-2026-06-03.md:51-69`). The decision it embodies is that "the control law" should be a first-class object selected per channel rather than a function the tick body hard-calls — so that a second, deliberately-different law (the worked PID example) can occupy the same socket. The interface D1 sketches keeps the existing result type and the existing five inputs, so the only line that changes in the tick body is the call itself; the loop that drives it (`for (auto& channel : context.channels)` at `tick_runner.cpp:221`), the sensor-event append, and `TryApplyChannelSetpoint` (`:244-254`) all stay put. Nothing below argues against FEAT-0003's standing — it argues about whether the seam, *if* drawn, sits where D1 says it does.

The "move, not a rewrite" claim checks out against the code. `EvaluateChannel` (`channel_evaluator.cpp:440-474`) is pure orchestration with no file or hardware I/O: it builds an `EvaluationScratch`, calls five file-private stage functions in fixed order (`EvaluatePrimarySetpoint` `:453`, `ApplyCpuOverride` `:454`, `UpdateDemandAndBoosts` `:466`, `ComputeFinalSetpoint` `:467`, `DetectAuthorityReassert` `:469`), copies a handful of fields onto `channel`, and returns a `ChannelEvaluation` by value (`:471-473`). Nothing in that body touches a file, a socket, or the fan writer — the write path is downstream in `TryApplyChannelSetpoint`. So wrapping this function as a method on a `CurveOverlayController` is, in the narrow mechanical sense, relocating a function body behind a vtable pointer. The signature already matches D1's proposed `Evaluate` byte-for-byte (`channel_evaluator.h:56-60`), which is why D1 can claim a one-call-site change honestly.

The real tension is not the wrap — it is that the seam D1 draws around the call site is the cheap third of the change, and the document is candid about this. Two things sit underneath: config and per-channel dynamic state are welded in one `ChannelState` struct (the curve law's `smoothed_demand_pct`, `boosts[]`, and the `low_band_*` block live beside law-agnostic write fields like `write_active` at `control_runtime_context.h:25`), and the output conditioning a second law would want to share — the rate limiter (`channel_evaluator.cpp:37-70`) and EMA smoothing (`:72-117`) — is currently inline inside the curve law rather than extracted. So the seam at line 241 is real and well-placed, but it does not by itself let a PID drop in; the state-ownership refactor and the conditioning split are the load-bearing work, and the plan's §2 says so explicitly. Calling the line-241 swap "the seam" risks overstating how much the seam alone buys.

The steelman for doing it anyway is the output contract. `ChannelEvaluation` (`channel_evaluator.h:30-47`) is genuinely law-agnostic: `has_setpoint`, `setpoint_pct`, `observed_temp_c`, `response_source`, the authority-reassert pair, the sensor-event fields, and `safety_override`. None of those name a curve, a boost, or an integral — a PID fills the same struct, and every downstream consumer (write gate, status, CSV) is untouched. That is a strong argument that the *output* side of the interface is stable enough to host laws "as different as possible," because the thing crossing the seam is a setpoint and some reporting flags, not a law-shaped payload. If you accept that the contract is the hard part of any abstraction and that it is already correct here, the line-241 swap is the natural place to cash it in.

The runtime cost is negligible, and that cuts in the seam's favor. The tick is 250 ms (`config/control.release.json:15`, `config/control.example.json:15`) and the release config carries six channels (ids 0–5 in that file), so the per-channel call happens six times per tick — 24 calls per second. One indirect call through a vtable versus a direct call, 24 times a second, is not a measurable cost against a control loop that does temperature sampling, curve interpolation, four leaky-integrator boosts, and a file write each tick; there is no inner loop where the virtual dispatch is hot. The cost objection to `IChannelController` is real only in principle, and at this tick rate and channel count it does not survive contact with the numbers.

Where I land (opinion): the seam is correctly placed and the "move, not a rewrite" framing is accurate *for the call site*, but the interesting risk is input leakage, not call cost — and here the signature does leak curve assumptions. The `Evaluate` signature passes `const RuntimeSnapshotIndex&`, yet inside `EvaluateChannel` that argument is consumed at exactly one place: `DetectAuthorityReassert` calls `s.runtime_index.FindFanChannel(...)` at `channel_evaluator.cpp:380` to read the observed fan state for drift detection. A PID computing `error = observed_temp_c − target_c` needs `TempInputs` (`control_policy.h:36-43`, cpu/gpu temps) and `now` (for the derivative's dt) — but it has no obvious use for the fan-snapshot index, which is an authority-reassert concern, not a control-law input. So one `Evaluate` signature *can* host both laws, but only because it is the union of what each needs, and authority-reassert is arguably output conditioning that leaked into the law signature rather than a law input. My opinion: the seam is sound, but the conditioning split should be drawn *before or with* the interface, or the first PID implementation inherits a `runtime_index` parameter it ignores — a small but real signal that the signature is curve-shaped, not law-neutral.

The single fact that would flip the "negligible cost / sound seam" view is empirical: if the maintainer ran with a channel count or tick rate far outside today's 6-channels-at-250 ms — say dozens of channels at a sub-50 ms tick (the loader warns below 50 ms at `control_loop_config.cpp:479-483`) — and a profiler showed the per-channel evaluation on the hot path, the virtual-call argument would acquire teeth and an alternative (a resolved-once function pointer, or templated dispatch) would deserve weighing. Equally, on the design side, if a third law needed an input that is neither in `TempInputs` nor derivable from `now` and `RuntimeSnapshotIndex`, the claim that this exact signature hosts laws "as different as possible" would break, and the interface — not just its implementations — would have to change.

## State decouple: slimming ChannelState, and reset-on-swap

`ChannelState` (`control_runtime_context.h:17-84`) is one struct that welds the channel's `config` (`:18`) to the curve law's per-tick carry-over state: `smoothed_demand_pct` (`:32`, the EMA's previous value, read at `channel_evaluator.cpp:309` and written back at `:312`), `boosts[]` (`:35`, four leaky integrators read at `:317` and rewritten at `:315`), and the `low_band_*` accumulator block (`:53-69`). D2 decides to move that dynamic state out of `ChannelState` into `CurveOverlayController` and slim the struct to law-agnostic fields, "full decouple in one pass" (`profile-hot-swap-decision-2026-06-03.md:86-107`). D5 decides that on a swap each channel's law state is reset by default, carry-over opt-in and out of the first slice (`:155-165`). Together they answer "where does a PID integral live, and what happens to the old curve's smoothing when the law changes" — with "in the controller" and "it is discarded."

**The real tension** is one-pass versus interim against a bit-identity constraint. The boost-sum at `channel_evaluator.cpp:353-364` is operand-ordered for byte-identical output, with a load-bearing comment citing `CONTROL_PIPELINE_MATH.md §5`; REQ-PROFILE-01 makes "output identical to today's `EvaluateChannel`" the gate. D2 itself names the cost: the larger first change "must reproduce today's `EvaluateChannel` output exactly" (`:104-106`). So the tension is not abstract design taste — the decouple touches the exact fields and the exact arithmetic that an equivalence test pins, and any relocation of `smoothed_demand_pct`/`boosts[]` that perturbs read-order, NaN-seeding (`:43-45`, `:76-78`), or operand grouping fails that gate.

**Steelman for an interim instead of one pass.** A two-step path — introduce `IChannelController` wrapping the curve law while it still reads/writes the existing `ChannelState` fields, *then* relocate the fields in a follow-up — keeps the seam-introduction diff free of any field move, so the equivalence test isolates exactly one variable at a time. The plan's own §6 step 2 already couples "wrap as a controller" with "move the curve-law dynamic state off `ChannelState`" (plan §6 step 2); splitting those would mean a failing equivalence test points at either the indirection or the move, never both. D2 rejects this on the grounds of "one end state rather than an interim with welded curve state" (`:101-103`) — a maintainability argument, not a correctness one.

**What it actually costs** is more than D2's three-field list implies, in two concrete ways. First, the `low_band_*` block (`control_runtime_context.h:53-69`) that D2 assigns to `CurveOverlayController` is not written by the curve evaluator at all — `low_band_stage_boost_pct` is produced by `UpdateLowBandState` in `low_band_integrator.cpp:196`, called at `tick_runner.cpp:203` as a separate stage *before* `EvaluateChannel` at `:241`; the evaluator only *reads* it (`channel_evaluator.cpp:330,346`). So "the controller owns the `low_band_*` accumulators" (`:93-94`) cannot be a pure field-move; it requires either relocating the low-band integrator stage into the controller or leaving an owner/reader split across a module boundary. Second, the `last_raw_demand_pct` gap D2 left open needed a reporting-specific clarification, now recorded in D2 and FEAT-0003.

**On `last_raw_demand_pct` specifically (opinion, grounded):** the original plan §7 called it a curve-law EMA input, but the code does not support that. It is set once at `channel_evaluator.cpp:457` from the per-tick scratch `raw_desired_setpoint` and is never read back into any computation — its only readers are reporting (`runtime_status.cpp:25`, `control_status_writer.cpp:21`, dashboard `feedforward_pct`). The EMA's actual carry-over input is `smoothed_demand_pct` (`:309`), not `last_raw_demand_pct`. The honest classification is therefore: curve-law-produced telemetry. It must not be treated as a generic, always-meaningful `ChannelState` reporting field for PID; a future decouple can store it in the curve controller or expose it through a kind-aware/nullable reporting envelope, but status/CSV must not publish a misleading `feedforward_pct` for a feedback law.

**Where I land on reset-by-default (D5): it is the right default, and the rate-limiter argument is load-bearing but partial.** D5's safety claim is that "the shared output stage still rate-limits the first post-swap setpoint, so reset does not produce an unbounded step" (`:165`). That holds *only* because the rate limiter reads `last_issued_pct` (`channel_evaluator.cpp:367`), which is owned by the write path (`channel_write.cpp:142,367`), is law-agnostic under D2 (`:96`), and is therefore *not* cleared by D5's law-state reset — so the bound survives the swap. The caveat: `RateLimitSetpoint` returns the desired value unbounded when `last_issued_pct` is NaN (`:43-45`), i.e. on a channel that has never written; a swap on a never-written channel gets no slew bound from this path, only the `[0,100]` clamp at `:353-364`. That is an edge, but it means "reset is always bounded by the rate limiter" is true for writing channels and not for first-write channels.

**Would any law want carry-over? (opinion).** For a law *change* (curve→PID), no: a carried `smoothed_demand_pct` or a `boosts[]` integrator value has no PID meaning (D5's rationale, `:162-164`), and reset is the only defined-meaning option. For a same-law re-tune (curve→curve with new gains), carry-over of `boosts[]` and `smoothed_demand_pct` would preserve a warmed integrator and avoid a re-converge transient — that is the one case where carry-over has a defensible motive, and it is exactly the case D5 pushes to opt-in (`:160-161`). I think reset-by-default is still correct there, because a re-tune that changed a boost's rate constants would carry an integrator value computed under the old constants, which is its own silent inconsistency; starting from a defined zero is the predictable floor D5 names.

**What single fact would flip me.** On reset-vs-carry-over: if a measurement showed the post-swap re-converge transient on a *writing* channel moves the duty fast enough to cross `MEASUREMENT_GATE.md` baseline characterization between ticks despite the rate limiter — i.e. the slew bound is not tight enough to keep a reset swap inside the gate — then carry-over (or a swap-time seed of `smoothed_demand_pct` from `last_issued_pct`) would become the safer default, not the opt-in. On the one-pass decision: if the equivalence harness for REQ-PROFILE-01 cannot be written to cover the `low_band_*` owner/reader split across `low_band_integrator.cpp` and the controller in a single bit-identical assertion, the interim (seam first, field-move second) becomes the lower-risk path D2 rejected.

## The conditioning split: what is "the law" vs shared safety

The element is D4 and the §1 "law-vs-conditioning" table: the decision to draw a line through `EvaluateChannel` so that some stages travel with whatever control law is installed and some are shared safety that every law inherits unchanged. D4 puts eight stages firmly on the law-agnostic side — clamp, sensor-safe mode, deadband, write cooldown, control-hold, circuit breaker, baseline capture/restore, and the write gate (`docs/profile-hot-swap-decision-2026-06-03.md:139-146`) — and records two *leans* on the still-open stages: the rise/fall/max-step rate limiter is leaned shared as a "safety slew clamp," and the EMA demand smoothing plus decay latch is leaned curve-law-specific (`:147-153`). The plan's §2 restates this and then concedes the load-bearing point: "That split is **not drawn in code today**" (plan §2). The whole demonstration ordering rests on this — §6 step 1 is "extract shared output conditioning from the curve law" with a bit-identity gate *before* any second law exists (plan §6 step 1), so if the split is mis-drawn, the first slice extracts the wrong seam.

I verified the split against source, and it largely holds with two real frictions. The sensor-safe latch is genuinely law-agnostic in spirit: `EvaluatePrimarySetpoint` forces `kSafeModeFanDuty` and sets `safety_override = true` after `kMaxConsecutiveSensorFailures` (`channel_evaluator.cpp:248-264`), and the write path honors that flag by letting the command bypass an open breaker (`channel_write.cpp:307`). Nothing in that logic is curve-shaped — it is "I lost my input, command full duty" — so a PID would want exactly the same behavior. The rate limiter is also defensible as shared: `RateLimitSetpoint` bounds the move of the *final* setpoint away from `last_issued_pct` using `elapsed_since_last_write_ms` (`channel_evaluator.cpp:366-371`), i.e. it clamps the slew of the value actually sent to hardware against the last value actually written, which is a property of the actuator, not of how the number was computed. EMA smoothing, by contrast, is curve-internal: `ApplyDemandSmoothing` runs asymmetric rise/fall alphas and a decay-latch floor on `smoothed_demand_pct` (`:72-117`), feeding the boost-sum — it is part of how the curve law *shapes* demand, not a safety floor.

The real tension is the clamp, and here the doc's own framing is partly aspirational. D4 calls "clamp to `[min_duty_pct, 100]`" law-agnostic shared output (`:141-143`), but in current code there is no shared `[min_duty_pct, 100]` stage. The curve law's internal sum clamps to a hard `[0.0, 100.0]` (`channel_evaluator.cpp:353-364`), and the `min_duty_pct` floor lives *inside the curve law itself* — it is the `min_floor_pct` argument to `LookupCurve`, applied at `control_policy.cpp:99-100`. The write path (`channel_write.cpp:269-370`) does deadband, cooldown, baseline, runtime-allows, and breaker — but it never re-applies a min-duty floor. So today `min_duty_pct` is a curve-law parameter, not shared conditioning; D4's "shared clamp" is the proposed end state, and getting there is itself part of the extraction, not a free inheritance.

The strongest case for the alternative — that *some* smoothing is law-agnostic — is not a vibe; it has a concrete mechanism. The decay latch (`:101-113`) caps how fast demand may *fall* (`decay_latch_pct_per_min`), and a fall-rate floor is the same category of protection as the rate limiter's fall clamp: both exist so duty does not collapse too fast under a transient dip. If you accept the rate limiter as shared "a mis-tuned law should not move duty arbitrarily fast" safety (D4's own rationale, `:148-150`), the symmetric argument says a *minimum* responsiveness/anti-collapse floor is also something every law wants, and stranding it inside the curve law means a PID silently loses anti-collapse protection it would otherwise inherit. That is the steelman for "EMA-as-curve-specific is too coarse": the *latch* may be safety even if the *rise/fall alphas* are law shape.

What it costs to act on the split is concrete and double-edged. The rate-limiter-as-shared lean creates a fight-for-authority risk: if the rate limiter is a post-law stage and a `PidController` "expects to own its own dynamics" (its integral and derivative *are* a rate model), then a fall-rate clamp downstream silently overrides the PID's intended descent — the PID computes a step the slew clamp refuses to honor, the integral keeps accumulating against a setpoint that never lands, and you get windup the PID's own anti-windup (D3c, `decision:129-132`) cannot see because the truncation happens *after* the controller returns. They do fight, and the fight is invisible to the law. The opinion I hold: D4's leans are correctly oriented but under-specified on exactly this interaction — "shared slew clamp" needs to define whether the law is *told* its output was clamped, or the same windup the doc fixes inside PID reappears at the seam. The extraction cost is bounded: the boost-sum operand order at `:353-364` is locked bit-identical by REQ-PROFILE-01, so the equivalence test catches a botched curve extraction — but no test today exercises a *second* law against the shared stages, so the rate-limiter/PID interaction is unguarded by construction.

Where I land (opinion): the split is roughly right but the boundary D4 draws is cleaner on paper than the code supports, and two specific items should move or be re-examined before any extraction — `min_duty_pct` (today a curve-law floor in `LookupCurve`, not a shared clamp) and the decay latch (a fall-rate floor that is arguably the same safety category as the rate limiter D4 already shares). To be explicit about scope: *if* the seam is ever extracted, the §6-step-1 "shared conditioning" bundle as currently named would extract a boundary that doesn't match where `min_duty_pct` and the latch actually live, and the bit-identity gate would not catch that because it only protects the curve law against itself.

The single fact that would flip my view on the central question — "is rate-limiter-as-shared safe, or do law and clamp fight?" — is the answer to whether the slew clamp feeds its truncation back to the controller. If the seam is defined so a law receives its previous *clamped* output as the state it integrates against (so the PID's next-tick error already reflects what hardware actually got), then the clamp and the law do not fight and "shared slew clamp" is correct as written; if the law integrates against its own *unclamped* intended output, they fight and the rate limiter cannot be purely shared without giving the law a windup-aware hook. That one design fact — closed-loop state = issued vs intended — decides it, and it is exactly the fact D4's "lean shared" does not yet pin down.

## PID as the worked example: is it the right stress test?

The element is a methodological choice, not a feature: the decision record names PID "a feedback law as different from the current feed-forward curve as possible" and designs the `IChannelController` seam against that breadth "rather than curve-specific" (`docs/profile-hot-swap-decision-2026-06-03.md:3-8`). D3 then collapses P/PI/PD/PID into one class by gain selection (a zero gain disables a term), with three refinements: D3a makes the baseline selectable — `"curve"` gives `output = curve(temp) + PID(error)`, `"fixed"` gives `output = bias_pct + PID(error)` (`:117-124`); D3b leans derivative-on-measurement to avoid a setpoint-change derivative kick when `target_c` is swapped live (`:126-128`); D3c leans an integral clamp plus conditional integration that stops accumulating while the output saturates (`:129-132`). The decision these embody is that the worst-case tenant of the seam is a stateful feedback regulator, so if the seam can host PID it can host anything milder. None of this exists in code: a search for `Kp/Ki/Kd`, `target_c` as a regulated setpoint, `PidController`, or any `IChannelController`/`controller` discriminator returns no matches in `src/`.

The real tension is whether "most stateful" equals "most different from the seam's point of view," and those are not the same axis. The current law is feed-forward and *monotone-additive* in `curve(temp)`: `EvaluateChannel` composes `EvaluatePrimarySetpoint` → `ApplyCpuOverride` → `UpdateDemandAndBoosts` → `ComputeFinalSetpoint` (`src/control/channel_evaluator.cpp:453-467`); the primary value is a temperature→duty lookup (`LookupCurve`, `src/policy/control_policy.cpp:68-101`); the CPU override is max-wins and "cannot lower demand" (`channel_evaluator.cpp:295-300`); the four boost overlays only add, summed in a load-bearing operand order (`:353-364`); and the rate limiter only bounds the slew (`:37-70`). Every stage takes the instantaneous temperature vector and produces a duty that rises with temperature. PID shares more of that shape than the framing admits: it still maps the same primary temperature (D3 keeps `SelectPrimaryCurveInput`, `:198-237`, shared) to a duty, still clamps to `[min_duty_pct, 100]`, still passes the shared slew clamp. What PID adds is one genuinely new property — *history dependence through the integral accumulator* — which is real, but it is the same property the existing boost overlays and the low-band stage already have: those are leaky integrators carrying `boosts[]` and `low_band_*` state across ticks (`UpdateDemandAndBoosts`, `:314-320`; `low_band_integrator.cpp:138-193`). The seam already has to carry per-tick accumulator state. PID's novelty over the *current* law is narrower than "as different as possible" suggests.

The strongest case for a different worked example is a bang-bang / hysteresis law, because it breaks an assumption PID preserves. Steelman: every existing stage is continuous and monotone in temperature, and PID — being `bias + Kp·error + Ki·∫error + Kd·d/dt` — is *also* continuous and (term-wise) monotone in error. A hysteresis law is neither: its output depends on a latched discrete state (which side of the band it last crossed), so the same temperature can map to two different duties, and the shared slew clamp (`:37-70`) and EMA smoothing (`:72-117`) that PID tolerates would actively fight a law whose whole point is a fast discontinuous edge. That is the kind of mismatch that exposes whether the seam's shared output conditioning (D4) is genuinely law-agnostic or quietly curve-shaped. An RPM-feedback law stresses a *different* seam again: it regulates against a tachometer reading, not a temperature, so it would break the shared `SelectPrimaryCurveInput` input contract that D3 explicitly reuses — the one place D3 assumed all laws agree. Both alternatives probe a seam edge PID leaves untouched, which is the substance of the worry that designing around PID yields a PID-shaped seam: an interface validated only against a continuous error-driven law may bake in "the law consumes a primary temperature and emits a slew-limitable continuous duty" as a silent precondition.

What this actually costs in *this* codebase is asymmetric, and that asymmetry is the decisive trade-off. PID is the cheapest non-trivial law to host because it reuses the most existing structure: the same `ChannelEvaluation` output contract (`channel_evaluator.h:30-47`), the same input selection (`:198-237`), the same clamp and slew clamp, and an accumulator pattern the boost stages already prove the state plumbing supports. Its one new cost — an integral/derivative accumulator with no field to live in — is precisely the cost D2 already absorbs by moving dynamic state off `ChannelState` into the controller (`docs/profile-hot-swap-decision-2026-06-03.md:86-107`). A hysteresis or RPM law would force *additional* seam surface that does not exist: a discrete latched-state lifecycle the `Reset()` contract (decision `:66`) would have to define, or a non-temperature input the shared `SelectPrimaryCurveInput` does not provide. So the alternatives are better *stress tests* exactly because they cost more — they would surface seam assumptions PID never touches — but that same extra cost is why none of them is the natural first demonstration tenant.

Where I land (opinion): PID is the right *first* worked example but the wrong *sole* one, and the doc slightly oversells it by calling it "as different as possible." It is the most-different law that still fits the existing input/output/clamp contract, which makes it the right thing to *build first* — it validates the state-ownership refactor (D2) and the dispatch seam without also demanding a new input source or a discrete-state lifecycle. But "fits the existing contract" is the very reason it cannot, alone, prove the seam isn't PID-shaped; a seam tested only by a law that respects all of PID's preconditions will pass even if it has silently encoded those preconditions. The honest framing (proposal) is that PID is the *load-bearing* example and a hysteresis or RPM law is the *adversarial* one, and the abstraction's law-agnosticism is only demonstrated when at least one adversarial law is at least sketched against the seam — even on paper.

On the D3a sub-question specifically — is `curve(temp) + PID(error)` still "a different law" or just the curve law with a correction term — my read is that the `"curve"` form is *the curve law plus a feedback trim*, not a different law, and the decision record's own algebra says so: the curve "stays as the shape/floor" and PID "corrects" it (`:117-119`). That form reuses `LookupCurve` (`control_policy.cpp:68-101`) for the baseline and adds one error-driven term on top, which is structurally the same move the four boost overlays already make — add a temperature-driven correction to `curve(temp)` (`channel_evaluator.cpp:353-364`) — except the correction is now closed-loop. The `"fixed"` form (`bias_pct + PID(error)`) is the one that is genuinely a different law, because it discards `curve(temp)` as the baseline entirely and lets the regulator own the resting duty. So D3a actually contains both the weakest and the strongest version of "different law" inside one switch, and the seam is only really stress-tested by the `"fixed"` branch; the `"curve"` branch is close enough to the existing additive composition that it would mostly re-exercise the curve path. The single fact that would flip my overall view: if a tachometer/RPM input were already plumbed into the control inputs as a regulatable signal (it is not — `rpm`/`tach` appear only as logged telemetry in `runtime_snapshot.*` and CSV, never as a control setpoint), then a closed-loop RPM law would be nearly as cheap to host as PID, and PID's claim to be the *maximally* different affordable example would no longer hold.

## The measurement gate: shadow/dry-run and allow_live

> **Resolved 2026-06-06.** This section analyzes D6's *original*
> `allow_live`-without-evidence posture. The maintainer adopted its conclusion:
> D6 was revised so `pid.allow_live: true` is rejected at config load unless the
> channel has the characterization evidence (a shadow-log comparison against the
> curve baseline is accepted as that evidence) **and** a non-NaN slew cap —
> closing both the evidence-vs-consent gap (reading the gate as an evidence gate)
> and the NaN-default slew-cap gap argued below. The analysis below is kept as the
> reasoning that produced the revision; see the revised D6
> (`docs/profile-hot-swap-decision-2026-06-03.md`) and
> `docs/profile-hot-swap-allow-live-decision-2026-06-06.md`.

This element analyzed the original D6 posture for how a PID channel earned the right to write the fan. That original shape was: a PID channel defaulted to shadow/dry-run — it computed and logged a setpoint but suppressed the write — and `pid.allow_live: true` was a per-channel operator opt-in that authorized live writes immediately, before characterization evidence existed. The claim was that this stayed inside the `docs/MEASUREMENT_GATE.md` invariant ("shipped live behavior is the measured baseline") because the crossing was explicit and recorded: `allow_live` was in config and would emit `control_loop.profile_applied` naming the channel and law. None of this exists in code — there is no `allow_live`, no shadow path, no `IChannelController` or `PidController` in `src/control/` (grep finds only unrelated uses of the word controller — the process supervisor, the config-print, and the Super I/O / GPU hardware controllers — none a control-law discriminator).

The real tension was that `docs/MEASUREMENT_GATE.md` is an *evidence* gate, not a *consent* gate. Read it directly: it blocks expansion until "cadence data exists," "fan-write response has been rechecked," and "a compact summary records the data that justified the change" (`MEASUREMENT_GATE.md:72-85`); its exit criteria are measurements, not authorizations. The original D6 substituted operator intent for that evidence, so `allow_live` did not satisfy the gate on the gate's own terms; it made crossing it a one-keystroke, logged act. "Explicit and recorded" answers *who moved the baseline and when*, which is an accountability property. It does not answer *was it safe to move*, which is what the gate's exit criteria are about. An audit trail that a thing happened is not evidence the thing was characterized.

The steelman for D6 is genuine, and it is the FEAT-0003 §5 framing (REQ-PROFILE-07): shadow/dry-run is the mechanism that *produces* the evidence the gate wants. A shadow PID selects the same primary temperature as the curve law (`SelectPrimaryCurveInput`, `channel_evaluator.cpp:198-237`, shared per D3 `:135-137`) and logs its would-be setpoint each tick, so an operator could overlay the PID trajectory on the actual curve trajectory for the same inputs and decide whether PID is sane before any write. On that reading `allow_live` is not a bypass — it is the switch you flip *after* you have read the shadow logs, and keeping it per-channel means one experimental channel can go live while the other five stay on the characterized curve. The gate stays a real gate; `allow_live` is just the gate's latch.

But that steelman is exactly where the mechanism is thin, and the cost is concrete. The opinion I hold: "shadow computes and logs but suppresses the write" is verifiable evidence only that the PID *ran and produced numbers*, not that it is *safe to write live* — because the load-bearing safety behavior is in the closed loop the shadow path by definition does not close. PID is feedback: `error = temp − target`, integral accumulates over time (`decision:36-38`). A shadow integral winds against an error history the fan never actually corrected, so the shadow trajectory and the live trajectory diverge precisely in the integral/derivative terms that make feedback dangerous. The shadow log shows what PID computed against a temperature curve some *other* controller was driving; it cannot show the limit cycle (a sustained duty oscillation the feedback loop settles into), overshoot, or windup that only appear once PID's own output starts moving the temperature it reads. D6 itself leans toward derivative-on-measurement and integral anti-windup *because* live setpoint swaps cause derivative kick and saturation (D3b/D3c, `decision:126-132`) — those are the failure modes shadow mode structurally cannot exhibit. So the evidence shadow produces is necessary-but-not-sufficient, and `allow_live` lets an operator treat "it logged plausibly" as "it is characterized," which is the substitution the gate exists to prevent.

That leaves the shared safety floor as the backstop, and here the file:line cost is sharpest. D6 names clamp, slew cap, sensor-safe, and breaker as the floor. Three of those four are unconditional and would hold for any law: the final clamp is hard-coded `std::clamp(..., 0.0, 100.0)` (`channel_evaluator.cpp:353-364`); sensor-safe forces 100% at 3 failures (`channel_evaluator.cpp:248-264`, `control_runtime_context.h:82-83`); the breaker opens after 5 write failures (`channel_write.cpp:44-47`, `kMaxConsecutiveFailures = 5u`, `control_runtime_context.h:78`). But the slew cap — the one floor D4 specifically wants shared because a mis-tuned PID should not be able to step duty arbitrarily fast — is opt-in config that defaults off. `rise_rate_pct_per_min`, `fall_rate_pct_per_min`, and `max_setpoint_step_pct` all default to `quiet_NaN()` (`control_loop.h:29-31`), are validated `allow_nan = true` so an unset value passes (`control_loop_config.cpp:241-246`), and `RateLimitSetpoint` returns the desired value unmodified when the rate is NaN (`channel_evaluator.cpp:55-57`). So on a channel whose config omits these fields, the "safety slew clamp" is absent: an `allow_live` PID could step 0→100 in one tick, bounded only by the `[0,100]` clamp. The 2026-06-06 D6 revision makes that exact gap a config-load precondition.

Where I land (opinion, now resolved into the docs): the original `allow_live` posture made crossing the gate convenient and auditable, but not evidenced, and its compensating slew floor was configuration-dependent rather than guaranteed. The resolved design does the right thing: `allow_live` requires characterization evidence and a non-NaN slew cap at config load. That makes the next target verification, not more prose — if this feature is ever promoted, the config-load test for REQ-PROFILE-07 must prove both missing-evidence and missing-slew cases reject before any live PID write can be configured.

## Proposal A: dispatch shape — hard-named switch vs registry table

The element is §3 of the deepening plan, which fills a gap D1 left open. D1 fixes the abstraction — `IChannelController` with `Evaluate`/`Reset`/`Kind` (`docs/profile-hot-swap-decision-2026-06-03.md:51-69`) — but never settles how a per-channel `controller` string becomes a controller instance. §3 names two shapes for that mapping: **A1**, a `controller` string parsed to a `ControllerKind` enum throw-on-unknown plus a construction `switch`, explicitly modeled on `ParseCurveShape`; and **A2**, a registration table mapping `controller` string → `{config-parser, factory}`, claimed to mirror `kBoostStageSpecs`. The decision §3 embodies is its recommendation: "A1 now, reversible to A2," with the A1↔A2 choice held private behind one `MakeChannelController(...)` factory so a later promotion "touches one factory function" (plan §3). Both shapes are net-new: there is no law dispatch in the loader today — `LoadChannelConfig` (`src/control/control_loop_config.cpp:407-472`) is a flat monomorphic parse that reads every field unconditionally.

The real tension is between two costs that point opposite directions. A1 spreads each new law across three named edit sites — the enum, the construction `switch`, and a per-law config branch (`:159`); that is the cost the word "modular" is reacting against, because adding a law means touching shared code rather than dropping in a self-contained unit. A2 removes those edit sites at the price of one indirection layer — a table plus a registration unit (`:171-174`) — whose lookup, ordering, and registration-timing you now have to reason about even when only two laws exist. The honest question is not which reads better but at what law count A2's saved edits exceed its standing indirection, and whether "reversible at one factory function" is actually true given where a per-law config block has to live.

The strongest case for A2 (steelman): a registry is the shape that matches the operator's own word, "modular," in its strict sense — a new control function becomes a *registered* unit rather than a set of diffs threaded through `LoadChannelConfig`, the construction switch, and `ChannelState` slimming. If the demonstration is meant to *show* that the per-channel seam can host an open-ended *range* of laws — which is exactly the recorded intent, "PID stands in as the worked example of how different a swappable control law may be" (`docs/profile-hot-swap-decision-2026-06-03.md` §Selected directions) — then a table that names its extension point makes that range legible in a way a `switch` does not. A2 also localizes the blast radius: a malformed or experimental third law is one self-contained registration, so the existing two laws are not reopened to add it. And if out-of-translation-unit registration ever becomes the goal (a law contributed without editing the loader's `switch`), only A2 supports it at all; A1 cannot express it. In a world where the law count is genuinely open, A2 is the shape that stops re-litigating the dispatch site on every addition.

What A2 actually costs in *this* codebase is larger than §3 implies, because the cited precedent does not do what A2 needs. `kBoostStageSpecs` is a `constexpr std::array<BoostStageSpec, kBoostStageCount>` (`src/control/boost_stage.h:58-72`) iterated by **fixed index in lockstep** — `for (i = 0; i < kBoostStageCount; ++i)` at config load (`control_loop_config.cpp:445-448`), at validation (`:258-260`), at CSV (`src/runtime/runtime_csv_rows.cpp:615-617`), at status (`src/runtime/runtime_status.cpp:32-34`). The `name` field on each spec builds column keys; it is never a dispatch key. There is no `find_if`, no `.at(name)`, no string lookup, and no registration over those specs anywhere in `src/control` (verified by search). So A2's "registry / factory table mapping a string → {parser, factory}" is a *keyed* dispatch pattern the repo does not currently contain; `kBoostStageSpecs` is parallel-array iteration over a compile-time-fixed set, which is closer to A1's spirit (a closed, in-file enumeration) than to A2's. A2 would introduce a string-keyed indirection that has no precedent here, not "mirror" an existing one. (Plan §3 already disclaims this kinship — it notes `kBoostStageSpecs` "is a fixed array indexed by enum, not a string-keyed selector"; the loose "matches `kBoostStageSpecs`" wording survives only in the plan's §7 Q1.)

The "reversible at one factory function" claim is where I part company with the recommendation, and the leak is concrete. The dispatch *construction* genuinely can hide behind `MakeChannelController(...)`: the call site (`tick_runner.cpp:241`), `ChannelEvaluation`, and the controllers do not see the switch-vs-table choice, so that part of §3 is right. But a second law is not only a construction; it is a `pid` config block with `target_c`, `kp`, `ki`, `kd`, anti-windup bounds, and `feedforward`/`bias` (`docs/features/FEAT-0003-selectable-profile-hot-swap.md` §7). That block must be *parsed* and *validated*, and both `LoadChannelConfig` (`control_loop_config.cpp:407-472`) and `ValidateChannelConfig` (`:231-287`) are flat monomorphic functions today. A per-law parse/validate branch has to land in those two functions regardless of whether construction is A1 or A2 — and *that* is the surface the "modular" framing most wants to avoid editing per law. A2 only escapes it if the registry entry carries its own parser and validator and the loader delegates by key (which is precisely the registration unit A2 admits it adds, plan §3). So the reversible-at-one-function story holds for the factory but not for config parsing/validation: the registry shape, to deliver its promise, has to reach into the loader, not just the factory. A1→A2 is reversible at the *construction* seam and not at the *parse/validate* seam; §3 conflates the two.

Where I land (opinion): for a **two-law** demonstration, no registry is justified, and A1 is the better starting shape — not because it is "simpler" as a vibe, but on a countable trade-off. A1's added edit sites would scale with law count; at two laws (`curve_overlay`, `pid` — the only kinds FEAT-0003 names, plan §3) the per-law edit cost is two `switch` arms and two parse branches, which is below the standing cost of a keyed-lookup layer the repo has no instance of and no test for. A registry earns its indirection when one of two concrete triggers fires: (a) the law count crosses roughly **four or more** kinds, where the linear edit-site growth of A1 and the risk of a missed `switch`/parse/validate arm start to dominate; or (b) **out-of-translation-unit registration** becomes an actual goal — a law added without editing the loader — which A1 structurally could not express and which is the only capability A2 would uniquely buy. Neither trigger is present: FEAT-0003 names two laws and no plugin/external-law requirement, and the plan's own ordering puts "promote A1 → A2" as step 6, explicitly gated on "a third law or external registration is wanted" (plan §6). Building the more elaborate shape first would be the wrong direction for a feature whose status is "any implementation would be a demonstration."

On the framing: A1 does not betray "modular," it honors it pragmatically — provided "A1 now" is read with the leak above in view. The modular property the seam would deliver is the `IChannelController` boundary itself (one virtual call replacing `tick_runner.cpp:241`), the law-agnostic `ChannelEvaluation` contract (`channel_evaluator.h:30-47`), and per-controller state ownership (D2, `docs/profile-hot-swap-decision-2026-06-03.md:86-107`); none of those depend on whether *selection* is a `switch` or a table. "Modular" is about the laws being separable units, which A1 would already give; the dispatch shape is a second-order detail. The honest caveat is that §3's "reversible at one factory" undersells what a third law costs under A1, since the parse/validate branches are not behind the factory — so the recommendation should say "A1 now, and a third law reopens the loader regardless; promote to A2 at that point so the loader is reopened *once* to delegate by key." The single fact that would flip me to "start with A2": a stated requirement that control laws be registrable **without editing the loader** — an external/plugin law, or a credible near-term law count of four-plus. Absent that fact in FEAT-0003 or D1–D7, A1-first is the position the evidence supports.

## Proposal B: what a "profile" is, and the whole-profile atomic swap

The element in §4 of the plan asks two questions D7 left open: what *object* a "profile" is to an operator, and how it arrives. D7 only fixed the *apply order* — validate via `LoadControlLoopConfig`, take a channel-set delta, then build-reset-swap at a tick boundary (`docs/profile-hot-swap-decision-2026-06-03.md` §D7) — and assumed a profile object without naming it. The plan's §4 answers with three candidate forms (B1 inline full config, B2 named on-disk file, B3 delta/overlay) and lands on B2 plus a `--profile <name>` startup selector mirroring `--config`. The decision that proposal embodies is that a profile *would* be a whole `control_loop` config body, swapped for **every** channel at once at one tick boundary, so no tick ever runs a half-applied profile. None of this exists today: `--config` is the only flag the supervisor bakes into the worker command line (`src/control/control_supervisor.cpp:259-270`, key at `:267-268`), the arg parser knows `--config` (`src/app/app_args.cpp:129`) and has no `--profile` token, and there is no profile request file or controller seam. So every claim below is conditional and stated as would/could.

The real tension is not which of B1/B2/B3 wins — it is that there are already **two** different things both called a "profile," and they would arrive as two different request files. FEAT-0001 (Accepted) treats a profile as the *write policy* — `writes_enabled` and `blocked_channels` — and proposes its own flat-root request file `write_policy.request.json` (`docs/features/FEAT-0001-hot-swap-write-policy.md` §7). FEAT-0003 (Draft) treats a profile as the *control law plus parameters* and proposes `profile.request.json` (`docs/features/FEAT-0003-selectable-profile-hot-swap.md` §7). These gate orthogonal things: FEAT-0001 decides whether a computed setpoint is written, FEAT-0003 decides what setpoint is computed. And the two specs define each other out by name — FEAT-0001 lists "General control-profile switching" as a non-goal (`FEAT-0001:65-66`) and FEAT-0003 lists "Changing the write policy" as a non-goal (`FEAT-0003:104-106`). That mutual exclusion is the sharpest fact in this whole area: the codebase is already heading toward two profile concepts and two intake files, and §4's "a profile is a whole `control_loop` config" framing quietly assumes a single concept that the Accepted feature next door contradicts.

The strongest case for merging them into one profile concept and one request file is operator coherence. An operator who wants to take a channel offline does not naturally distinguish "I am changing the write policy" from "I am changing the control law" — both are "I am changing how this channel behaves." A single `profile.request.json` carrying both the law block and the write-policy block would let one atomic request reconfigure a channel end to end, and the breaker-reset intake the plan reuses is already single-shot and tick-aligned (`ProcessCircuitBreakerResetRequest` is called once at `src/control/tick_runner.cpp:195`, after snapshot sampling and before the per-channel loop, so it cannot interleave with an in-flight write — `src/runtime/runtime_lifecycle.cpp:55-103`). One file, one validation gate, one event stream is a coherent operator surface, and it is the natural reading of "a profile is the whole `control_loop` config."

What that coupling actually costs in this codebase is the decisive point against it. FEAT-0001 is Accepted and FEAT-0003 is not (`FEAT-0001:4` vs `FEAT-0003:4`). Merging them would bind an authorized, schedulable feature to an unscheduled demonstration through a shared request schema and a shared apply path — the Accepted feature could not ship its write-policy hot-swap without dragging in (or stubbing around) a control-law seam that does not exist. There is a second concrete cost in the "whole `control_loop` config" framing itself: a full config body carries fields that are explicitly out of scope to change live — `poll_tick_ms` and the construction-time consumers like the CSV identity block (`docs/profile-hot-swap-decision-2026-06-03.md` §Consequences) — so B1/B2 would each need a disallowed-delta check to reject a candidate that changed them. The law-block-only alternative avoids that check but then needs a merge layer to graft the law block onto the running config, which is B3, the form the plan itself rejects as needing a merge-and-revalidate layer that does not exist (plan §4, B-form 3).

Where I land (opinion) — as a design choice conditional on a demonstration being built, not a recommendation to build one — is: **two request files, not one.** The mutual-non-goal fact and the Accepted-vs-Draft asymmetry both point the same way; coupling an Accepted feature's schema to an unscheduled one is a cost paid now for coherence that may never be exercised, and the two gates are genuinely independent computations. On the *form* sub-question I diverge from the plan's B2-as-primary lean for a demonstration specifically: `LoadControlLoopConfig` already validates a full config body (`src/control/control_loop_config.cpp:507-568`), so B1 inline adds the least net-new machinery, whereas B2's `--profile <name>` is a name→path *resolver layer* on top of what `--config` already does (`control_supervisor.cpp:267-268`) — net-new code, not a new capability — and B3 needs a merger. B2 buys a durable, auditable source-of-record for the active profile; B1 buys lower code at the cost of having no such record. For a throwaway demonstration B1 is the lower-cost form; B2 only earns its resolver if the profiles must outlive the process as named artifacts.

On the "all channels vs one" sub-question, atomicity and scope are separable and the plan slightly conflates them. Atomicity means no *half-applied* profile is visible within a tick; that is satisfied by applying at the tick boundary regardless of how many channels change. The breaker-reset template both specs mirror already carries a per-channel selector — `RequestRuntimeBreakerReset` takes `std::optional<std::uint32_t> channel` (`src/runtime/runtime_lifecycle.cpp:40-53`) and the take path parses it (`:69-96`) — so a per-channel profile request is already expressible in the precedent, and the safer operator default (change one channel, leave the rest characterized) does not require giving up atomicity. My opinion is that "rebuild ALL controllers at once" is the riskier framing for a feature whose own measurement gate worries about switching a *writing* channel to an uncharacterized law (`FEAT-0003:117`, REQ-PROFILE-07): an all-channel swap maximizes the blast radius of a single bad candidate, and the precedent already supports the narrower scope.

Two single facts would flip each branch. On **one-vs-two concepts**: if any real operator workflow ever needs to change write policy and control law in *one atomic action* — block a channel and re-law it as a single indivisible step — then the two-file split is wrong and a merged request is justified despite the Accepted/Draft coupling cost; absent such a workflow, two files stand. On **form**: if a demonstration needs a durable, auditable record of the active profile that survives restart, B2's resolver earns its cost and `--profile` is justified; if the demonstration is throwaway and the active profile need not be a named artifact, B1 inline is the lower-code form and `--config` already carries the startup profile with no resolver to write.

## Reuse machinery and intake ergonomics

The element is the proposal (plan §5, §4) that a whole-profile swap reuse the breaker-reset request-intake rather than invent a second operator channel. That intake **is** implemented and single-shot: `TakeRuntimeBreakerResetRequest` (`runtime_lifecycle.cpp:55-103`) parses the request, stores any failure as `parse_error` instead of rethrowing (`:97-99`), and then **unconditionally** clears the file at `:101` — so a malformed request is deleted on the same pass that rejects it. The tick consumes it at exactly one point, `tick_runner.cpp:195`, before the per-channel loop, on a straight-line single-threaded tick. The decision the proposal embodies is "don't build new machinery": a profile request **would** be taken once at the same site and applied at the tick boundary (plan §5, D7). That reuse is the strongest part of the proposal, because the consumption point and the atomicity it buys already exist and are load-bearing for the breaker reset.

The real tension is whether single-shot intake — "consumed and rejected once, never retried" — fits a *profile swap* the way it fits a *breaker reset*. For the breaker reset, take-then-clear-on-error (`:101` running after the catch at `:97-99`) is defensible because the request carries almost nothing (a `requested_at` string and an optional `channel`, `:68-96`); a malformed one costs the operator a one-line re-issue. A profile swap is a heavier authored artifact. If it is rejected and deleted in one tick, the operator's work is gone, and the only signal is the proposed `control_loop.profile_rejected` event — there is no file left to inspect or correct in place.

The steelman for *not* mirroring single-shot — i.e. keep the rejected file, or retry — rests on a concrete failure mode: a profile change is an operator decision an operator may want to debug, and delete-on-error throws away the exact bytes that failed. Retaining the file (or moving it aside) would let the operator diff the malformed request against a known-good one rather than reconstruct it from an event string. That is a genuine ergonomic gain, not a vibe: it is the difference between "the artifact that failed is on disk" and "the artifact is gone and you have a log line."

What the alternative actually costs cuts the other way, though, and the cost is measurable per tick. If the intake did **not** clear on error (drop the unconditional `:101` for the profile path), a single poison request would be re-read and re-rejected every `poll_tick_ms` — one `profile_rejected` event per tick until an operator manually removes the file. The single-shot delete at `:101` is precisely what prevents that event flood. So the choice is: single-shot (lose the authored file, emit one rejection) versus retain/retry (preserve the file, emit a rejection every tick). My opinion: single-shot — including delete-on-error — is the right ergonomics for the profile swap *as well*, **conditioned on** the request being a thin named reference (plan §4 B-form 2, `{ "profile": "<name>" }`). Under that form the deleted file is a pointer, and the durable artifact (the named profile file) survives; re-issue is one explicit operator action, which is consistent with treating every applied/rejected change as an audited event (FEAT-0003 §4). The flip fact: if the primary surface were B-form 1 (an inline full config body, plan §4), delete-on-error would be worth reconsidering, because then the deleted bytes *are* the hand-authored config, not a recoverable pointer — at that point preserve-or-move-aside earns its cost.

On the flat-vs-subdir rider (Q4): every request and state file in the repo today is flat at the runtime-home root — `stop.request.json` (`runtime_lifecycle.cpp:17`), `circuit_breaker_reset.request.json` (`:22`), `pending_writes.json`, `control_runtime.json` — and a repo-wide search finds no `runtime/requests/` directory; only `logs/` and `logs/archive/` use subdirs. Both specs float a `runtime/requests/` subdir, but introducing it for one new file would either create a mixed convention (one request under a subdir, three at the root) or force a migration of the existing flat files to stay consistent. My opinion: keep the profile request flat, matching the grep'd precedent; the subdir's only gain is grouping, and there is nothing yet to group. The flip fact: if several new request files are coming at once, grouping them under `runtime/requests/` from the start would justify the new convention.

The second arc is the FEAT-0001 dependency. The plan's §5 table marks the breaker-intake template and `HandleExpiredHoldRestore` as *implemented* (`channel_write.cpp:186-257`), and that holds: it calls `RestoreSavedState` at `:205` and clears `write_active` at `:221`. But it is gated on hold-expiry — it returns early unless `write_active && effective_hold_ms != 0 && now_steady >= channel.hold_deadline && baseline_captured` (`:197-202`) — so it cannot be invoked as-is to drop a channel mid-profile-swap. What FEAT-0001 owns is not the restore *primitive* but the policy-swap *orchestration* that would call restore outside the hold-expiry path; FEAT-0001 is recorded **Accepted** but unbuilt (`FEAT-0001-hot-swap-write-policy.md:4`).

So "a chunk of FEAT-0003 is blocked on an unbuilt feature" overstates it, and the precise version is my landing. The first slice — law/param swap on a **fixed** channel set — needs nothing from FEAT-0001; only the channel-set slice (add/remove/reorder) does, and REQ-PROFILE-09 already fences it: a candidate whose channel set differs **must** be rejected when FEAT-0001 is absent (FEAT-0003 §6, REQ-PROFILE-09; D7 step 2). The coupling is therefore partial (the restore primitive exists; the generalized invocation does not), elective (the plan *chooses* to reuse FEAT-0001's choreography rather than build a second restore-invocation path), and fenced (no half-built state is reachable, because the differing-channel-set request is rejected outright). My opinion: this is a bounded ordering constraint, not a blocking one. The flip fact: if FEAT-0003's *motivation* were runtime channel reconfiguration rather than swapping the control law on a stable channel set, the FEAT-0001 dependency would gate the core value instead of an out-of-scope slice, and the ordering coupling would become a real problem worth resolving before any demonstration began.

## The dependency order: seam-extraction-first, bit-identity gated

The element is §6's claim that the first slice of any FEAT-0003 demonstration is not a new module bolted beside the live law but a refactor *of* the live law: step 1 pulls the law-agnostic output conditioning D4 names (the clamp, the sensor-safe latch and `safety_override`, the rate limiter as a slew clamp) out of `channel_evaluator.cpp` into a shared stage applied after any law, while the EMA smoothing + decay latch (`channel_evaluator.cpp:72-117`) stay curve-specific. The decision it embodies is ordering-as-honesty: §2 establishes that config and dynamic state are welded (`control_runtime_context.h:17-84`) and that conditioning is inline, so the plan refuses to call the second law an "additive drop-in" and instead front-loads the disturbance to the one piece of code that actually writes fans. The gate on step 1 is that the existing test lanes stay green and the curve output is "bit-identical," with the load-bearing boost-sum at `channel_evaluator.cpp:353-364` as the thing being protected — its comment (`:339-343`) ties the fixed left-to-right operand order to staying "bit-identical to pre-table builds," cross-referenced to `CONTROL_PIPELINE_MATH.md §5`/§8.2 (`docs/CONTROL_PIPELINE_MATH.md:497-504`).

The real tension is that step 1 is a pure refactor that touches the live control law — the function reached at exactly one call site, `tick_runner.cpp:241-243`, whose output `TryApplyChannelSetpoint` turns into real fan duty — for a doubted feature. Output-equivalent or not, you are reorganizing the exact arithmetic that `CONTROL_PIPELINE_MATH.md` is the byte-identity reference for, ahead of any law that would justify the reorganization. The ordering that makes the demonstration honest (do the disruptive part first, before the part anyone wanted) is the same ordering that maximizes risk-before-payoff: if the demonstration stalls after step 1, the repo is left carrying a moved safety/law boundary and a new shared stage with no PID to show for it.

The strongest case for doing step 1 first anyway — the steelman — is that the boundary it draws is real regardless of PID. Right now `safety_override` is set inside the curve law's primary-setpoint path (`channel_evaluator.cpp:248-264`), the sensor-safe forced-100% lives there, the clamp and rate limiter (`:353-364`, `:37-70`) are interleaved with curve-specific smoothing, and the comment at `:259-262` already has to reason about why the safety flag survives all the *later* curve stages ("cpu_override caps at 100%... boosts only add, so the flag stays valid to the end"). That comment is evidence the safety property is currently proven by tracing the whole curve law, not by structure. Extracting conditioning would let the safety floor be argued once, independent of whatever produces the raw setpoint — a separation of "what keeps fans safe" from "what decides fan speed" that has standalone maintenance value even if PID never ships. And the plan is not inventing the pattern: the `kBoostStageSpecs` table extraction was exactly this kind of behavior-preserving refactor, gated by an equivalence test (`tests/cpp/boost_stage_tests.cpp:1-7`), and it landed.

What it costs in this codebase is concentrated in what "bit-identical" can actually be proven to mean. The boost-sum at `:353-364` is a six-operand floating-point sum whose order is load-bearing precisely because floating-point addition is not associative; the comment defends the *order*, not the values. Step 1 leaves that sum inside the curve law (it is curve-specific composition, not shared conditioning), so step 1 itself need not reorder it — but the gate's strength is what the equivalence test checks, and the precedent the plan cites as the bit-identity gate, `boost_stage_tests.cpp`, asserts with `ExpectNear(..., kFpEpsilon)` where `kFpEpsilon = 1e-12` (`tests/cpp/boost_stage_tests.cpp:134,177,360`), i.e. a tolerance, not `==`. So "bit-identical over representative inputs" is, in the one existing precedent, *near*-identical over a hand-built input sequence (`:5-7`). Opinion: a 1e-12 tolerance over representative inputs is a strong regression net but does not prove zero behavior change — it cannot, because the property the comment protects (operand order) is exactly the property a tolerance is designed to forgive, and "representative" is a chosen list, not the input space. Where the extraction *does* bite is the clamp and the rate limiter moving from inside the law to after it: the rate limiter keys off `elapsed_since_last_write_ms` (`:366-371`), and any change to where in the per-channel sequence the clamp/slew is applied is a behavior change a near-equality assertion on the final setpoint would catch only if the representative inputs drive the clamp and slew boundaries.

Where I land (opinion): step 1 has standalone value as a separation of safety-floor from setpoint-derivation, and I would defend it on its own merits — but only if the gate is upgraded past the cited precedent, and even then I would not start it under the current FEAT-0003 status. Concretely (proposal): the equivalence gate for the *curve-specific* arithmetic that is merely relocated, not restructured, should assert exact equality (`==` on the `double`, or an integer-ULP check), reserving `ExpectNear` only for paths where an intended numeric difference exists — none should, since step 1 claims to introduce none. That is a stronger claim than `boost_stage_tests.cpp` makes and is the honest meaning of "bit-identical." With that gate, step 1 is a defensible refactor whose payoff (a once-argued safety boundary, the `safety_override`-survives-the-pipeline reasoning at `:259-262` replaced by structure) does not depend on PID ever existing. Without it, "bit-identical" is boosterism the maintainer's recorded doubt should reject. The position rests on the concrete trade-off between a moved live-law boundary now and a deferred, doubted feature later — not on the refactor being "cleaner."

What single fact would flip my view: if an exact-equality (ULP/`==`) output-equivalence harness over the curve law already existed and were green — not the `1e-12` tolerance in `boost_stage_tests.cpp` — then the floating-point objection to step 1's gate collapses, and the only remaining cost is the disturbance-to-live-code-before-payoff ordering itself. At that point I would treat step 1 as a low-marginal-cost cleanup worth doing on its own merits whenever the maintainer next opens this file for an unrelated reason, decoupled entirely from whether PID is ever scheduled. (Note: the proposal to tighten the gate to exact equality is mine to flag, not a reviewed conclusion.)

## The 8 open questions: which matter, which are bikeshedding

§7 is the residue of the grounding pass: eight items the D1–D7 decision record does not settle. The element embodies a specific editorial decision — to surface every unsettled seam rather than silently pick defaults — and the question worth asking back is whether all eight deserve a maintainer's attention or whether the document inflated its own open-question count. Triaged against the code, they split four ways: one genuine externally-visible fork (Q2), a cluster that is *forced* by existing constraints and only needs a rubber-stamp (Q1, Q3, Q6), two low-stakes conventions settled by one-line precedent (Q4, Q5), and two defects resolved by the 2026-06-06 paper cleanup (Q7, Q8). The triage is only about decision-cost *if* the demonstration were built.

The real tension sits in Q2 (the profile object). It is the one question whose answer would be externally visible and hard to reverse: a `controller` config key, a request-file shape, and an optional `--profile <name>` flag (FEAT-0003 §7/§8, `:197-221`) all leak into the operator surface, and once operators author profiles against one form, changing it breaks their files. The steepest steelman for the inline-body form (B-form 1) is that it needs no new on-disk convention and reuses `LoadControlLoopConfig` directly; the steelman for the delta form (B-form 3) is the smallest request payload. But B-form 3 would need a merge-and-revalidate layer that does not exist (plan §4 B-form 3), and the named-on-disk form (B-form 2) matches the one durable precedent already in the tree — the supervisor bakes a single `--config <path>` into the worker command line (`control_supervisor.cpp:259-270`; plan §1). My position: Q2 is the only §7 item that genuinely warrants a maintainer minute, and B-form 2 is the cheap default because it reuses the `--config` path precedent and gives each profile a durable source of record. What would flip me: if the demonstration only ever needs ad-hoc one-off bodies and never a named, reusable profile, B-form 1 alone would be the smaller surface.

Q1 (dispatch shape) reads like an architecture fork but is closer to bikeshedding, because the plan's own §3 argues the choice is reversible in one function. A1 (enum + `switch`, matching `ParseCurveShape` at `control_loop_config.cpp:423-426`) versus A2 (registry table, matching `kBoostStageSpecs` at `:258-260`) does not change the call site (`tick_runner.cpp:241`), the `ChannelEvaluation` contract, or the controllers — so A1→A2 would touch one `MakeChannelController` factory later (plan §3). For a two-law demonstration that names exactly `curve_overlay` and `pid`, A1 is the cheap default and the indirection of A2 earns nothing yet. This is a "just pick A1" question — the only fact that would promote it to a real fork is the dispatch leaking into the config schema or operator surface, which for two laws it does not. (The fuller dispatch-shape argument is in the Proposal A section above.)

Q3 and Q6 are not forks at all; they are *forced*, and asking them is close to a rubber-stamp. Q3 (channel-set changes in slice 1) is already answered by REQ-PROFILE-09 (`:192`): a channel-set change reuses FEAT-0001's restore/capture choreography, and FEAT-0001 is spec-only, not implemented (plan §5). You cannot add or drop a channel safely without a path that does not exist, so slice 1 *must* be a fixed channel set — the question is dictated by a missing dependency, not chosen. Q6 (seam-extraction-first) is similarly constrained: REQ-PROFILE-01 demands bit-identical curve output (`:184`), and the two §2 facts — config/state welding (`control_runtime_context.h:17-84`) and inline conditioning (sensor-safe `channel_evaluator.cpp:248-264`, EMA `:72-117`, rate limiter `:37-70`) — mean a second law cannot be an additive drop-in without first extracting the shared stage. I would call Q3 a pure rubber-stamp and Q6 a moderate-but-largely-foreclosed sequencing confirmation; the drop-in alternative to Q6 is the only thing that would make it a live choice, and the bit-identity gate plus the welding forecloses it.

Q4 and Q5 are the genuine bikeshedding — a maintainer can settle each in one sentence from precedent. Q4 (flat file vs. `runtime/requests/` subdir): every implemented request file is flat at the runtime-home root — `stop.request.json` (`runtime_lifecycle.cpp:17`) and `circuit_breaker_reset.request.json` (`:22`) — and no `runtime/requests/` directory exists, so flat wins by matching the only convention in the tree. Q5 (single-shot ergonomics): the breaker-reset take deletes the request file even on parse error (`runtime_lifecycle.cpp:101`), so a mirrored profile intake that consumes-and-rejects-once would match the established operator contract. Both are "pick the existing precedent and move on" — they do not change the design and should not consume a decision cycle.

Q7 and Q8 are both resolved on paper after the 2026-06-06 cleanup. Q7 (the `last_raw_demand_pct` field): the corrected classification is curve-law-produced telemetry, not an EMA input and not a law-agnostic reporting value. D2 now records that it should move with the curve controller or be exposed through a kind-aware/nullable reporting field, and REQ-PROFILE-08 now requires law-specific status/CSV fields not to publish stale or misleading values for PID channels. (The state section above develops this resolution.)

Q8 was the strongest original finding, but it should no longer be carried as an open contradiction. The discussion review found that the old D6 posture made `allow_live` a consent gate while REQ-PROFILE-07 and `MEASUREMENT_GATE.md` wanted evidence; the 2026-06-06 resolution revised D6, FEAT-0003, `docs/TRACEABILITY.md`, and the deepening plan's §7-8 so live PID now requires both characterization evidence and a non-NaN slew cap. The remaining work is to keep this section historical and ensure any future implementation tests the stricter gate.

## Where this nets out

The seam is worth designing, and the doc earns its keep — not as a build runway but as a decision-durability artifact that answers "can't we just swap in a PID?" once, with grounding, so it stops being re-litigated. The `IChannelController` boundary is genuinely well-placed (one call site at `tick_runner.cpp:241-243`, a law-agnostic `ChannelEvaluation` contract), and the virtual-call cost is a non-issue at 6 channels × 250 ms. But the seam is the cheap third of the work: the load-bearing parts are the `ChannelState` state-ownership refactor and the conditioning split, and the plan's own analysis is honest that a second law is not an additive drop-in. Step-1 conditioning-extraction has real standalone merit, but only if the bit-identity gate is tightened past the cited `1e-12`-tolerance precedent to exact equality; even then it spends re-verification risk on the live forced-100%-on-sensor-loss path to ship nothing observable, so it is not worth *starting* under the current status. The maintainer's decision is therefore not "build it" or "delete it" but "keep it on paper, characterized and unbuilt."
