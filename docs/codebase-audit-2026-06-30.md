# svg-mb-control codebase audit (2026-06-30)

## Executive summary

The control core, config-composition, and analyze subsystems are structurally sound, but the audit surfaced four high-severity defects that bear directly on thermal safety and operational reliability. Two false-cold sensor gaps (GPU thermal path, AMD Tctl offset decode) and a rate-limited/cooldown-gated safe-mode path mean the engine can, under specific degraded-sensor or misconfiguration conditions, command minimum or slowly-rising fan duty on a hot part without tripping its own safe-mode machinery. None of these are triggered by the shipped configuration in steady state, but all are reachable from realistic transient hardware faults, a single overlay edit, or a backward clock step. The engine is broadly safe to run on the shipped config today, but it should not be considered fail-safe against sensor degradation or runtime crashes until the GPU validity gate, the safe-mode bypass, and the crash-latch backstop are addressed.

> Method: 7 subsystem reviewers fanned out across the engine at HEAD `dc54a60`; each finding was then handed to an independent adversarial verifier instructed to refute it (default REFUTED). 18 findings raised → **12 confirmed**, 6 refuted, 0 uncertain. This report lists only confirmed findings.

### 1. GPU false-cold 0 C drives fans to minimum (high)
**Scenario.** On a `GpuOnly` (or source-aware CPU-dropped) channel cooling a hot GPU, the undocumented-NVAPI thermal read fails transiently (backend not ready, discovery mask momentarily 0, or `thermals_.read()` fails), but `GpuProbe::sample_thermal_fast` (`third_party/.../gpu_probe.cpp:457-468`) still returns `true` for a valid index. `core_c/memjn_c/hotspot_c` keep their `GpuSnapshot` defaults of 0.0; `GpuReader::Sample()` (`src/hardware/gpu_reader.cpp:636`) emits `available=true` with 0 C. `GpuControlEnvelopeC` (`src/control/channel_evaluator.cpp:449-455`) returns 0, the curve is looked up at 0 C, and the fan is driven to min duty. Because `available` was true, no sensor-miss is counted and the 3-miss safe-mode trip never fires. This is the exact false-cold class the AMD path was hardened against in PR #33, but here the garbage read is presented as a *valid* 0 C.
**Fix.** Add a GPU-side validity gate in `GpuReader::Sample()`: treat a thermal-fast sample whose `core_c/memjn_c` (and `hotspot_c` when present) are all <= a small floor as `available=false`, so the channel sees the GPU input as ABSENT and the existing sensor-miss/safe-mode machinery runs. Alternatively have `GpuProbe` distinguish "read succeeded" from "returned true for valid index" and propagate per-field validity.

### 2. Safe-mode 100% is rate-limited and cooldown-gated (high)
**Scenario.** A channel steady at 30% on a hot part goes sensor-blind for 3 ticks. `EvaluatePrimarySetpoint` (`channel_evaluator.cpp:166`) sets `raw_desired_setpoint = kSafeModeFanDuty` (100%) and `safety_override = true`. But that setpoint still flows through `ApplyDemandSmoothing` and `RateLimitSetpoint`, which apply `max_setpoint_step_pct=0.6` / `rise_rate_pct_per_min=75` from `config/control.release.json`, capping the rise to ~0.31%/tick. `safety_override` is consulted in exactly one place — `channel_write.cpp:316`, to bypass the write-failure breaker — and does *not* bypass the deadband, write-cooldown, or rate limiter. The fan takes tens of seconds to actually reach 100% while the blind part heats, and the event log records "entering safe mode (100% duty)" (`channel_write.cpp:164`) that the actuator has not achieved.
**Fix.** When `safety_override` is set, bypass demand smoothing and the rate limiter (set the final setpoint to `kSafeModeFanDuty` directly), and bypass the write-cooldown/deadband gates in `TryApplyChannelSetpoint` so the safe-mode write is issued immediately rather than deferred.

### 3. Overlay coverage of base controlled channels is not enforced (high)
**Scenario.** `ComposeConfigRoot` (`src/control/profile_composition.cpp:94`) iterates only the overlay's channels and throws solely when an overlay channel is *not* a base-controlled channel. It never checks the reverse — that every base-controlled fan (numeric `release_min_duty_pct`, direction != `excluded`) appears in the overlay. An operator who deletes the channel-4 (`front_radiator_intake_noctua`, base floor 24%) block from `release.behavior.json` still gets a config that composes and loads successfully; that fan produces no `ChannelControlConfig`, is never written by the control loop, and is never floored — a silent under-cooling regression with zero diagnostics. The shipped overlay lists all of channels 0-5, so it is not currently triggered.
**Fix.** After the injection loop, verify the overlay's channel-number set is a superset of `ControlledChannelMinDuty`'s keys and throw "machine base controls channel N but the behavior overlay does not list it" for any missing base-controlled channel.

### 4 & 5. Unbounded events-table growth + unprunable NULL-run_id rows (high)
These share one root cause — non-force event ingest is not idempotent — so they are fixed together.
**Scenario (#4).** `IngestEvents()` (`src/analyze/analyze_ingest.cpp:272`) always re-parses the full `svg_mb_control_events.jsonl` and unconditionally inserts every event; the `DELETE FROM events` is guarded by `options.force` only, and the events schema (`analyze_db.cpp:132-147`) has no UNIQUE constraint. Each periodic `analyze ingest` (no `--force`) over the same runtime home appends another full copy of the events file, so after N runs the table holds `events_per_file * N` rows — the Issue #4 unbounded-disk-growth mode FEAT-0015/0016 were meant to close. The regression test `test_ingest_is_idempotent_without_force` asserts every table count *except* events, so it gives false confidence.
**Scenario (#5).** Because the already-seen run is skipped, `run_windows` is empty, so `InsertEventsAttributed` (`src/analyze/analyze_ingest_db.cpp:301`) inserts every duplicate with `run_id = NULL`. FEAT-0016 prune deletes by `runs.id` via `ON DELETE CASCADE` (`analyze_db.cpp:134`) and never reaches NULL-run_id rows; `CountOrphanRows` even filters `WHERE e.run_id IS NOT NULL` (`analyze_prune.cpp:325`). So `analyze prune --db-retain-days 7` reports `db_orphan_rows=0` while thousands of unprunable duplicate events accumulate forever.
**Fix.** Make event ingest idempotent on the non-force path (clear/replace events for the affected runs, or add a dedup key such as `UNIQUE(run_id, event_time, event_type, detail)` with `INSERT OR IGNORE`, or skip the events phase when `run_windows` is empty), and add a retention path for unattributed events (`DELETE FROM events WHERE run_id IS NULL AND event_time < cutoff`) so FEAT-0016 actually bounds the table.

### 6. Crash-latch backoff leaves fans frozen up to 32 s (medium)
**Scenario.** A worker that previously passed startup crashes at runtime (`exit_code != 0`, not stop-requested). The crash skips the control-loop shutdown restore (which runs only on clean loop exit), and `sio_fan_writer.cpp:94` sets `restore_on_exit=false`, so the fan latches in manual mode at the last commanded duty with no BIOS curve. The supervisor (`src/control/control_supervisor.cpp:821`) then sleeps `min(60, 1<<min(restart_count,5))` = 2,4,8,16,32,32… s before respawning. During each backoff no worker samples temperature or drives fans, and no out-of-process backstop forces a safe duty. A recurring fault plus a load spike inside a <=32 s window lets the part heat with the fan stuck at a possibly-low idle duty. The project's own decision records (`docs/fan-restart-restore-and-plant-model-measurement-2026-06-20.md:45-49`) acknowledge this latched-no-fallback state.
**Fix.** On a crash exit, have the supervisor (or a lightweight failsafe) drive blocked/controlled channels to a safe high duty or hand off to BIOS auto before sleeping, and/or cap the backoff much lower so the uncontrolled window is bounded to a few seconds.

### 7. Spec-gate cannot detect duplicate FEAT registry rows (medium)
**Scenario.** `_registry_rows()` (`tests/test_feature_specs.py:93`) keys a dict by FEAT id, so two rows sharing an id collapse to the last. `test_feature_registry_matches_feature_specs` only asserts `sorted(registry) == sorted(specs)` (a key-set comparison, unchanged by a duplicate) plus per-field checks on the surviving row. A maintainer who copies an existing FEAT id (two `[FEAT-0026]` rows) keeps the Python lane green while the first row's namespace/status/path go unchecked — reproducing exactly the FEAT-0024/0025 collision PR #28 renumbered.
**Fix.** In `_registry_rows`, collect ids into a list before dedup and assert `len(ids) == len(set(ids))`, or have the test count raw `[FEAT-` rows and assert it equals `len(registry)`.

### 8. DecodeTctl validity gate has no lower bound (low)
**Scenario.** `DecodeTctl` (`src/hardware/amd_decode.h:37`) sets `*out_valid = (temp_field > 0 && temp < 125.0)` — an upper bound but no lower bound. On an offset-flag part, a small populated `temp_field` with bit `0x80000` set (e.g. `temp_field=8` → 1.0 − 49.0 = −48 C from a torn/glitched register read) passes the gate. The control path consumes −48 C as a real CPU temperature, evaluates the curve below its first point → minimum CPU duty, and counts no sensor miss. `DecodeCcdTemp` shares the no-lower-bound shape.
**Fix.** Add a physically-grounded lower bound to the `out_valid` predicate in `DecodeTctl` (and `DecodeCcdTemp`) — require `temp` above a small floor (e.g. 0 C or a configured minimum-plausible CPU temp) so an offset-corrected sub-ambient reading is dropped as implausible.

### 9. Event-log JSONL append not fsync'd (low)
**Scenario.** `AppendLineAtomic` (`src/runtime/runtime_event_log.cpp:365`) opens the JSONL with `FILE_APPEND_DATA|SYNCHRONIZE` and a single `WriteFile` (POSIX: `ofstream` flush), with no `FlushFileBuffers`/fsync and no write-through. Unlike `json_io.cpp:221-251`, which deliberately flushes before rename, the append path leaves the file-size metadata and data sectors non-atomic under power loss. A crash right after a critical event (`control_loop.write_failed`, `circuit_breaker_opened`) can leave the last line as partial/whitespace bytes, breaking a strict line-by-line parser or dropping the most safety-relevant record.
**Fix.** `FlushFileBuffers` the handle after `WriteFile` (accepting the per-event cost), or document and enforce that JSONL consumers must tolerate a torn final line, so durability matches the atomic JSON writers.

### 10. CSV archive/mirror rows not fsync'd (low)
**Scenario.** `FlushStreams` (`src/runtime/runtime_csv_archive.cpp:309`) calls only `ofstream::flush()` on plain (non-write-through) streams — data reaches the OS page cache but is not committed. The manifest, by contrast, is fsync-committed via `TryWriteJsonFileAtomic`. On power loss the durable manifest can report `row_count=N` while the most recent CSV rows are still in cache (lost) and the last physical row is torn, so an audit that trusts the manifest count against the CSV finds a mismatch with the newest thermal evidence missing.
**Fix.** Periodically `FlushFileBuffers` the archive handle (e.g. at each manifest update boundary), or stop asserting an exact `rows_written` in the synced manifest, so the durable manifest count cannot exceed what is durably present in the CSV.

### 11. Watchdog staleness uses local-time second-granularity timestamps (low)
**Scenario.** `AssessHealthState` (`src/runtime/runtime_health.cpp:184`) computes age as `system_clock::now() - ParseLocalIso8601(last_update)`; both format/parse use local civil time truncated to whole seconds with no UTC offset, and parse sets `tm_isdst=-1`. A worker wedges at 01:30 (fans latched) before a DST fall-back at 02:00; after the shift `now()` is ~1 hour earlier than the frozen timestamp, so age is negative, clamped to 0 (line 194), reported healthy → exit 0 → watchdog takes no action. The hung worker is not restarted for the duration of the backward-clock offset window.
**Fix.** Persist runtime timestamps in UTC (ISO-8601 `Z`) or carry a monotonic heartbeat counter, compute age from a monotonic source, and never clamp a negative age to fresh — treat an out-of-order timestamp as stale.

### 12. Build hard-requires vcpkg though no vcpkg dependency is consumed (low)
**Scenario.** There is no `vcpkg.json` and no `find_package` for any vcpkg library (CMake's only `find_package` is `Git QUIET`; nlohmann/json, sqlite3, SVG-MB-SIO, gpu_telemetry are all vendored under `third_party/`). Yet the CI "Configure vcpkg" step (`.github/workflows/ci-windows.yml:40`/61) and `Build-Release.ps1` (throws at line 242, passes the toolchain/triplet) make a missing vcpkg a hard build failure, using the toolchain only as a source of cmake/ninja/ctest that `Resolve-ToolFromPathOrVcpkg` already finds on PATH. On any Windows host or future runner image without vcpkg preinstalled and `VCPKG_ROOT` unset, the whole pipeline fails before configure even though MSVC/CMake/Ninja are present and sufficient.
**Fix.** Make vcpkg optional: set the toolchain file/triplet only when `VCPKG_ROOT` resolves, resolve cmake/ninja/ctest from PATH otherwise, and drop or downgrade the throwing "Configure vcpkg" gate since no vcpkg package is consumed.

## Uncertain / needs-hardware

None. No findings required hardware to confirm or were left in an uncertain state; every reported defect was grounded end-to-end in source at HEAD and survived adversarial verification.

## What was verified clean

**control-pipeline.** Beyond the safe-mode bypass defect (#2), the demand-smoothing, rate-limiting, deadband, write-cooldown, and circuit-breaker logic in `channel_evaluator.cpp`/`channel_write.cpp` was traced and found internally consistent for normal (non-safety-override) operation: the rise/fall smoothing, per-tick step caps, and breaker open/close transitions behave as configured, and `safety_override` correctly bypasses the write-failure breaker where it is consulted. The only gap is that the override does not also short-circuit the rate/cooldown/deadband path.

**sensor-path (AMD core decode).** The AMD SMN decode and the PR #33 hardening were traced: `DecodeTctl`/`DecodeCcdTemp` correctly reject a successful-but-zero SMN read (`temp_field==0`) and an over-range (`>=125 C`) read, dropping the CPU input to ABSENT so the 3-miss safe-mode trip can fire. The only residual gap is the missing *lower* bound on the offset path (#8); the upper-bound and zero-field gates are sound.

**config-composition.** Apart from the missing reverse-coverage check (#3), `ComposeConfigRoot` correctly injects per-channel `min_duty` from the machine base, rejects overlay channels that are not base-controlled, and the shipped `release.behavior.json` / `snd-desk.cooling.policy.json` pair has complete and consistent channel coverage (0-5 controlled, 6 excluded with null floor). `LoadControlLoopConfig`/`ValidateControlLoopConfig` reject an empty channel set and the FEAT-0023 reproduction test pins composed output against `control.release.json`.

**analyze-db (prune/attribution).** Outside the non-idempotent event ingest (#4/#5), the run-purge cascade, manifest-skip on already-seen runs, force-path full clear, and start-event-to-run attribution were traced and behave correctly: `--force` re-ingest deletes then re-inserts without duplication, run windows attribute events correctly on a fresh ingest, and `DELETE FROM runs` cascades to attributed (non-NULL) events as designed.

**runtime-writepath (atomic JSON).** The atomic JSON writers (`json_io.cpp` `WriteJsonFileAtomic`) were verified to flush (`FlushFileBuffers`) the temp file before rename, giving the manifest and config writers genuine crash durability. The two findings here (#9/#10) are specifically about the *append-only* JSONL and CSV streams that do not share this guarantee; the atomic-rename path itself is sound.

**app-lifecycle.** Apart from the crash-latch backoff (#6) and the local-time watchdog clamp (#11), the supervisor's startup-gate, clean-shutdown restore (which reverts fans to BIOS auto on a graceful exit), stop-request handling, and the FEAT-0008 watchdog restart/force-terminate escalation chain (`kStale` → exit 2 → `--restart` → escalate) were traced and behave as documented for the non-crash, monotonic-clock case.

**ci-build / spec-gate.** Aside from the duplicate-registry blind spot (#7) and the unnecessary vcpkg hard-requirement (#12), the spec-before-build governance gate enforces registry↔spec↔traceability key-set equality, per-field consistency on matched rows, and within-spec requirement-ID uniqueness; the vendored-dependency build graph (INTERFACE nlohmann/json, static sqlite3, `add_subdirectory` for SIO/gpu_telemetry) is self-contained and the current CI image builds and runs the full CTest + Python lanes.
